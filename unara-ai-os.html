AI Systems Project

Unara AI OS

A local-first AI assistant and orchestration platform built to coordinate models, agents, tools, files, voice interaction, workflows, and infrastructure through one system.

Project Story

Unara is my primary AI systems project and the place where I have been learning what it takes to build an AI product beyond a simple model wrapper. It combines software engineering, local model deployment, orchestration, voice interaction, automation, and infrastructure into one growing platform.

Building an AI Operating Layer

Unara started as a local assistant experiment and grew into a larger AI operating system built around orchestration. The goal is not to place a new skin over one chatbot, but to create a system that can coordinate models, tools, workflows, files, and infrastructure through one interface.

The current architecture uses a web dashboard and API layer around local AI services, background task processing, persistent data, and integrations that can be expanded as the system grows.

  • FastAPI backend
  • Next.js dashboard
  • Redis and Celery task processing
  • PostgreSQL persistence
  • Docker-based deployment
  • Ollama for local model inference

From Chatbot to Orchestrator

The project is designed around the idea that different jobs should not always be handled by one general model. Unara can route work toward specialized models or agent roles depending on the task, then bring those pieces back into one user experience.

This makes Unara a test bed for the same ideas I want to use in larger AI products: model routing, specialist behavior, tool use, structured responses, long-running tasks, and local-first control.

The design goal is a system that can decide which model, tool, or worker should handle a task instead of forcing every request through one generic assistant.

Voice and Live Interaction

A major part of Unara has been making AI interaction feel less like submitting prompts and more like communicating with a persistent system. I have worked on live partial transcription, verbal stop behavior, wake/listen states, and visual feedback for listening, thinking, and speaking.

Voice work also forced me to think about latency, interruption handling, UI state, and how the backend and frontend stay synchronized while the model is generating.

Tools, Files, and Real Work

Unara is being built to reach beyond conversation. The system is designed to work with files, local services, scheduled workflows, infrastructure, and external tools rather than only returning text.

One important direction is direct access to my NAS-backed Vault and project resources so the assistant can work from live local information instead of relying only on a chat context window.

  • Filesystem and NAS integration
  • Tool and API calls
  • Scheduled workflows
  • Local and cloud model access
  • Infrastructure-aware actions

Engineering the System

Unara has also become the project where I practice building larger software deliberately. I use separate services, automated backend and frontend testing, isolated experiments, and role-based development workflows so new features can be tested without destabilizing the working system.

That process has changed the project from a collection of experiments into an actively maintained software platform with clear components and repeatable development practices.

What This Project Is Teaching Me

Unara has taught me that building an AI product is mostly about the systems around the model: context, tools, routing, state, interfaces, validation, infrastructure, and reliable software behavior.

It is also the project connecting many of my other interests. My local AI experiments help improve the model layer, while the Grim Grid provides the networked infrastructure and storage that let the system stay available and useful outside a single computer.
